# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The rationale, rejected alternatives and "not measured" notes behind each rule below live in `internal/design-history.md` (a verbatim snapshot of the pre-slim file, gitignored, maintainer machine only). Read it only when you need the why; do not copy history back into this file.

## What This Repo Is

KAIROS is a documentation-only project: a collection of AI agent definition files (Markdown) and a VitePress documentation site. There is no compiled code, no test suite, and no runtime beyond the docs build, with one exception: `scripts/usage.mjs`, a dependency-free Node script behind `/kairos:usage`.

Deliverables:
- `agents/` — the agent instruction files (the framework artifact). `agents/team/` holds the 5 Layered Mode agents (Claude Code plugin only; folder and agent ids keep their v9.4 names on purpose, because saved `## KAIROS Pipeline` checklists and `Add:` overrides name them).
- `docs/` — the VitePress site that documents and exposes those agents.
- `.opencode/agents/` and `.kimi-code/agents/` — hand-maintained mirrors of the 17 core files in `agents/` (not `agents/team/`).
- `skills/`, `commands/`, `.claude-plugin/` — plugin parts (see below).

## Development Commands

```bash
npm install              # install VitePress + dependencies
npm run docs:dev         # local dev server with hot reload (http://localhost:5173)
npm run docs:build       # build static site → docs/.vitepress/dist/
npm run docs:preview     # preview production build locally
```

No linting, no tests, no compile step.

## Agent Files and Mirrors

Each `agents/*.md` is Markdown with YAML frontmatter (`name`, `description`, `tools`, `model`) consumed by Claude Code or other AI tools.

**OpenCode mirror (`.opencode/agents/`).** Counterpart of every `agents/*.md`, converted by hand (no script). Body byte-for-byte identical to the source; only frontmatter differs: no `name:`, `mode: primary|subagent`, provider-prefixed `model:`, `tools:` CSV translated to a `permission:` object. Mapping documented in `docs/setup/opencode.md`.

**Kimi Code mirror (`.kimi-code/agents/`).** Same discipline. Frontmatter is near-identical: `name:`, `description:`, `tools:` copy unchanged; only `model: opus` → `model_preference: primary` and `model: sonnet` → `model_preference: secondary` (symbolic, never concrete Claude ids). Mapping in `docs/setup/kimi-code.md`.

Rules for both: any edit to an `agents/*.md` body or frontmatter is mirrored in the same change; adding or removing a core agent adds or removes both counterparts; also update `docs/agent-files.md` (and `docs/agent-files-team.md` for team files), which embed the raw agent Markdown. `agents/team/` is deliberately not mirrored (nobody has run Layered Mode on OpenCode or Kimi); do not add it without a run showing the dispatch pattern works there.

## Pipeline

6-phase, human-gated pipeline plus optional 6b and standalone agents:

| Phase | Agent file | Output artifact |
|-------|-----------|----------------|
| Pre-A | `context-extractor-agent.md` | `00-context.md` |
| Pre-B | `impact-assessment-agent.md` | `00b-impact.md` |
| 1 | `pm-agent.md` | `01-requirements.md` |
| 2 | `architect-agent.md` | `02-architecture.md` |
| 3a | `implementer-tdd-agent.md` or `implementer-coder-agent.md` (PHASE 0 only) | `03-implementation-plan.md` |
| 3b | same agent, re-invoked with the approved plan | code + `03-implementation.md` |
| 4 | `code-reviewer-agent.md` (review wave) | `04-review.md` |
| 4.5 | `security-reviewer-agent.md` *(optional, review wave)* | `04b-security-review.md` |
| 5 | `test-verifier-agent.md` (review wave) | `05-test-verification.md` |
| 5b | `qa-plan-agent.md` *(optional)* | `05b-qa-plan.md` |
| 6 | `release-planner-agent.md` | `06-deployment-plan.md` |
| 6b | `documentation-agent.md` *(optional)* | `06b-documentation.md` |

Standalone, user-invoked, never auto-invoked by the orchestrator (Hard Constraint 4), with two exceptions dispatched at Step 0e with `mode: orchestrated` (agent skips its own gate, the orchestrator presents the artifact): `bug-triage-agent` (`00c-bug-triage.md`, entry point for a bug report; recommends where the fix re-enters; never fixes) and `impact-assessment-agent`. Fully standalone: `dependency-audit-agent` (`.kairos/_tech-debt.md`, periodic, never applies an upgrade), `retrospective-agent` (appends to `.kairos/_lessons.md`), `improvement-advisor-agent` (reads `_lessons.md`, proposes framework changes as `.kairos/decisions/ADR-*.md`, never edits `agents/*.md`; a human applies them).

### Phase rules

- **Phase 3 splits in two calls of the same agent.** 3a runs PHASE 0 only: writes `03-implementation-plan.md` (`phase: implementer-plan`, `status: pending_approval`) unconditionally, touches no source. The orchestrator owns the gate. 3b re-invokes with the approved plan. `implementer-lead-agent` splits at the same boundary.
- **Review wave (phases 4, 4.5, 5).** Active reviewers run in parallel on settled code, one combined gate, one Risk Disposition Loop over the three tables, one fix pass for every `Mitigate now` row, one recheck scoped to that fix, one auto-fix budget. Security findings never enter the automatic loop; they reach the implementer only through the gate. After at least one loop iteration the loop exits with a final pass of every active reviewer (`final_pass: true`).
  - Only `test-verifier-agent` executes the test suite in a wave; `code-reviewer-agent` does static checks and lint only. Independent suites (separate toolchains, own coverage output) start together; shared database, port or build directory run in sequence; end-to-end last and alone.
  - In a wave no reviewer touches the ledger. Each ends its artifact with a `## Ledger Update` block (format: `skills/artifact-template/SKILL.md` §5) and the orchestrator applies them one after another, allocating ids and keeping `🔴 open` when reviewers disagree.
  - Recheck selection reads the `## Files Written` rows of the fix pass and the `MUST — from` origins: `code-reviewer-agent` when the diff has a non-test file, `test-verifier-agent` when it has a test file or a row came from `05`, `security-reviewer-agent` when a row came from `04b` or the diff touches a file `04b` cites. Skipped reviewers are logged with the unmet condition; an unreadable diff runs all. The same fix pass is the only way code changes after the review wave.
  - A host without parallel dispatch runs the three in sequence; gate, fix pass and loop are unchanged.
- **Phase 5b (`qa-plan-agent`) runs once, after the review loop exits**, on settled code. Never before implementation (the implementer's PHASE 0 already derives test cases from `AC-n`), never folded into `test-verifier-agent` (it would regenerate each iteration). Inputs are another agent's real gap set (`05-test-verification.md`'s `## Uncovered` and AC mapping, `03-implementation.md` files), never the human's words. Notable rules:
  - `## Risks` admits five row kinds only: regression retest, `AC-n` not verifiable by hand, uncovered `VERIFICATION` row, open question the release depends on, `automatable gap`.
  - Two readers: the gate reads evidence (Summary, Coverage Complement, Risks); the tester reads product language only (screens, actions, visible outcomes; never a class, file, SQL object or pipeline id). A manual case checks an outcome through the product, never the mechanism. A precondition is reached through the product, prepared by a developer and named as such, or written up as a Risk row, never a tester step in dev tools.
  - Tester's part limits: 5 cases (3 in Lean Mode), one-line `Setup` naming each surface once, steps open with the surface label on multi-surface cases, `Expected` at most two parts each opening with its step number, developer preparation before step 1 and undoing after the last step. Complement items reach a tester only if no assertion can see the outcome or no developer environment can stage it; otherwise an `automatable gap` row goes through the fix pass.
  - Every manual case has a `Who` cell (`QA` or `QA + prep`); `## Preparation` holds shared preparation (`none, the cases are steps only` when empty). `test-verifier-agent` tags each `## Uncovered` row with `Route` (`QA`, `QA + prep`, `Dev`, `—`); a closable `Dev` row also becomes an `## Issues` row (category `coverage`, `medium`, at most three). The `qa-plan-agent` row fires on a `QA` or `QA + prep` row.
  - Empty tester's part is `delivery: none`: no `_qa-file.md` or `_qa-comment.md`, one printed line; the gate stays. Without `05-test-verification.md` (every `simple_fix`) the agent reads the tests `03-implementation.md` lists and cites an assertion it opened; an `AC-n` so covered is `covered by <file:line>`.
  - `_qa-file.md` is the tester's block of `05b-qa-plan.md` copied by command, never retyped; `_qa-comment.md` is Core plus a literal `{qa_pointer}` line. After the QA gate the orchestrator asks the delivery way (never for an epic or a run without an issue): comment, file attached to the issue (GitLab only, via `glab api --form`), or repository file at `<qa-dir>`. An epic gets one cumulative file `<qa-dir>/<epic>.md`; each child rewrites only its own `## <issue>` section and `## Issues` row. The agent never writes into the repository; the orchestrator hands the file to `documentation-agent` in passthrough mode.
  - `.kairos/_qa-regression.md` (project root) is the cumulative catalogue of manual cases (`QA-n`, `Area`, `Setup`); `qa-plan-agent` is its only writer and reader.
  - The `AC-n` itself is never dropped or rewritten to move choreography to QA; an `AC-n` states trigger and observable outcome. Choreography goes in the case's `Setup`; known setup is a `VERIFICATION` row in `constraints.md`.
- **`architect-agent` Behaviour Delta** runs only when the change alters what a user of an already-shipped flow observes (before and after, including the failure path); `N/A` otherwise. Every new limit becomes a constraint row naming its unit.
- **`implementer-coder-agent` is code-first**: writes code, then decides test by test from the plan's `## Test Decision`; must extend existing tests where the touched code has them; skipping tests needs a written reason visible at the plan gate. `implementer-tdd-agent` is test-first. `simple_fix` routes to the coder.
- **`documentation-agent`** is, after the Phase 3 implementer, the second writer outside `.kairos/`, scoped to docs (README/CHANGELOG/`docs/**`), never source. Phase 6b splits like Phase 3: `step: draft` writes `06b-documentation.md` and ledger rows only; the orchestrator runs the gate; on Approve the same agent is called with `step: write`, `gate: resolved`, applies the approved draft (never redrafts) and appends `## Docs Written`. In Verbatim passthrough mode (QA plan file, Step 10d project summary) it never runs a gate; the orchestrator owns it. For the summary it drafts (`step: summary`, never reading `_tracking.md` or `04b-security-review.md` beyond a one-line category) and proposes the path (`docs/kairos-summaries/` fallback).
- **`_issues.md`**: when no development follows (`areas` without `development`, or the prompt asks for issues), the last analysis agent that ran (`architect-agent`, else `pm-agent`) writes `_issues.md` in the layout of `skills/issue-text/SKILL.md`; no `Size:`/`Effort:`/`Areas:`/`Skip:`/`Epic:` lines. KAIROS never creates tracker issues.

## Orchestrator: derivation, gates, settings

The rules themselves are in `agents/orchestrator-agent.md` (the spec). Invariants to keep in mind when editing around it:

- **Agents are derived from facts, never picked from a menu.** One rule table lives in `orchestrator-agent.md`. `impact-assessment-agent` and `architect-agent` report facts in frontmatter (`domains`, `test_suite`, `contract_change`, `test_first`, `behaviour_delta`, `threat_rows`) and never name an agent. Facts are read in priority order: `02-architecture.md`, `00b-impact.md`, the orchestrator's filesystem checks. Decisions bind at Step 0e (pm, architect, code at all, code-reviewer), before 3a (implementer), at the Phase 3 gate (test-verifier, security-reviewer) and at the review gate (qa-plan, release-planner, documentation). Each late decision is printed with the rule that fired; a human correction is stored in `run.md` as an override and logged in `_tracking.md`.
- **A fact that exists only because the architect ran is absent by design when it did not** and counts as none (security and documentation fall back to domains, constraint categories, `contract_change`). A fact that should exist and does not still counts toward running the agent. A triage can raise the measured effort, never lower it.
- **A pipeline that already exists wins over the prompt**: the issue's `## KAIROS Pipeline` section (override block or checklist), an unfinished run's `ledger/run.md`, a checklist built with the manual picker. A prompt phrase that would set scope is ignored with one printed line when one exists. A checklist switches derivation off. A new template carries only `Effort:`, `Auto-fix:` and explicit `Skip:`/`Add:`; `Add:` beats every rule (decide each agent as skipped, added, then row and area). `Analysis: <folder>` only points (paths into every prompt, never content); it adds no skip and is no fact source.
- **Areas**: `analysis` (pm, architect), `development` (implementer), `review` (code-reviewer, security-reviewer, test-verifier), `delivery` (qa-plan, release-planner, documentation). `impact-assessment-agent` and `bug-triage-agent` belong to none. Rules stay the fine lever; areas only narrow. The area question comes after the Bug-Input Check and its triage gate; an approved `quick-fix` triage answers it. **Run Intent** phrases (IT and EN, whole words) answer it in advance; they set a per-run intent and never set `corrected`, so the write-back never offers them as `Areas:`. **Decide each step** turns each decision announcement into a `multiSelect` question with the rules' answer `(Recommended)`; stored through the same overrides; never saved; the implementer is excluded. **Choose the pipeline myself** produces a checklist (`derivation: off`) and a mandatory issue write-back (Jira: posted as comment plus printed block).
- **Impact assessment runs when a fact is needed** (`analysis` or `development` in `areas`, or ticked). It reads in proportion to size (one or two named files: those and their tests; short artifact for `XS`/`S`) and starts from a triage's evidence. A `review`/`delivery`-only run reads the change surface from `git diff`, takes `effort` from an explicit line, then the `size:` label, then `medium`. Answers at the Start Gate that add, remove or replace a file, test, flow or criterion, or name another measured value, re-run it (in doubt, re-run); a typed question is answered by the orchestrator, never filed as a `🔴 open` row. A re-run answers each objection in one `Feedback:` line with a `file:line`.
- **`effort` vs `size`**: `effort` (`simple_fix`, `medium`, `significant_rework`) decides Lean/Trimmed/Full; `size` (`XS`..`XL`, `XS`/`S`→`simple_fix`, `M`/`L`→`medium`, `XL`→`significant_rework`) is for people only, measures footprint never hours, is stamped as a `size:` label at the Start Gate, and nothing branches on it. A `Size:` line sets both; `Effort:` sets only `effort`. Claude Code's `effort:` frontmatter field (reasoning depth) is unrelated; only `qa-plan-agent` sets it (`medium`, Claude Code only, omitted from mirrors).
- **Fast start**: an issue with a `## KAIROS Pipeline` section announces instead of asking, unless an Escalate, an unknown fact, an architect skipped against its rule or an empty pipeline needs a human. A folder whose `run.md` is `in_progress`/`stopped` resumes without the folder question; a gate recorded as `gate_pending` is never skipped. The folder is found by issue key. One issue = one folder, one ledger; **Start a new run** archives the finished run to `runs/run-<k>/` (snapshot of `_tracking.md` and `run.md`), keeps `ledger/`, `00-context.md`, `00c-bug-triage.md`, and re-runs the impact assessment. `run.md` carries `run`, `started`, `scope`, `earlier_runs`, `earlier_names`, `in_flight`, `gate_pending`, `phase_gates`, `wave_gates`, `agent_decisions`, `layered_stage`, `layered_round`.
- **Waves and phase gates continue on signal.** After a `partial` wave, and at the triage, requirements and last-Phase-3 gates under `phase_gates: on_signal` (default for `simple_fix`/`medium`; `every_gate` for `significant_rework` and checklists without an Auto-fix line), the orchestrator runs every gate check and stops only on: a new risk row `medium`+, a new constraint row, a failing test, a file outside the plan, an Escalate, a contract failure, or the artifact's own signals. Architecture, plan, review, recheck, documentation and QA gates stay `ask`. Every continued gate logs `auto-accepted: <ids, or none>`; a gate that asked logs `auto-accepted` and `off-recommendation`. `wave_gates: every_wave` restores the old behaviour. The list is a first cut from three runs of one project; revisit against logs, do not extend by analogy.
- **Risk Disposition Loop**: every Risks/Issues/Findings table has a `Disposition` column resolved row by row before the whole-artifact gate. An **Escalate** is followed by one question per escalated row (own evidence and alternatives, `Keep it open and go on` / `Stop here` plus free field); an answer closes it as **Mitigate now** or **Accept**; keeping it open does not flip the recommended gate option; **Refute premise** still flips it to **Stop pipeline**. Rows a person answers must open with what is undecided in product or code words, name the concrete file or screen, give two or three alternatives with the recommended one first and keep local ids as a trace; the orchestrator resolves any internal id still standing before it asks (`skills/artifact-template/SKILL.md` §6).
- **Gates do not open artifacts**: they print the path; `open`/`apri` opens it and shows the gate again. Exception: `03-implementation-plan.md` opens automatically. A scope change is a `decisions.md` row whose Decision opens with `Scope:`.
- **An agent is complete when its call returns**, not when its report appears. The orchestrator writes `in_flight` into `run.md` before each dispatch and clears it on return; only the four agents with a recovery mode (both implementers, `implementer-lead-agent`, `documentation-agent`) get `recovery: true`; others are re-run from the first prompt. A `[Subagent hand-back]` is not a return: make a tool call (read `run.md`) and check `in_flight` against notifications at the start of every turn. The orchestrator closes the entry itself only when a hand-back arrived, its report has a final `status` (not `partial`), no test or build process works against the worktree and `git status` is stable; log `returned by hand-back`. A `continue` with no notification does not re-invoke; ask once whether the agent was stopped. After a compaction, re-read `ledger/run.md` and trust it over the summary.
- **Orchestrator writes**: only inside `.kairos/`, plus three narrow exceptions: Step 0c's Gitignore check (appends `.kairos/`, once, after explicit choice), Step 0f's Issue Write-back (merges the corrected `## KAIROS Pipeline` section into the issue description after the human picks **Add to the issue**; re-reads the description first, offers nothing when the result equals the issue; never touches other content), and the `size:` label at the Start Gate. Hard Constraint 1 allows two writers outside `.kairos/` for the framework as a whole (`implementer-*`, `documentation-agent`); do not add a third.
- **`_tracking.md`** (feature folder) is the file for the human, written by the orchestrator at every event, read by no agent and never used to decide anything: `## Status` and `## Issue Alignment` (derived, rewritten each event; every `AC-n` is `pending`/`covered`/`manual`/`gap`/`changed`/`dropped`/`later`), append-only `## Log` (one line per event, no blank lines; later events as `after run`), `## Phases` (one short section per phase from that artifact's `## Summary`). Step 10 finalizes it and offers to delete phase artifacts (never the ledger, never itself). Sections that restate ledger rows are derived views. Legacy: `ledger/audit-log.md` and `_recap.md` are read, never written.
- **`_usage.md`** (feature folder) is written by `scripts/usage.mjs` after every agent that returns: one row per agent call, total, flag on a model different from the configured one, an orchestrator-session table (an upper bound), and a Peak ctx column. No model retypes a number. `--feature` is repeatable; `run.md`'s `earlier_names` holds names from a folder rename, written in the same edit as the rename.
- **Project settings** live in `.kairos-cfg/config` (`key: value` lines: `model.<agent>`, `manual-qa`, `qa-dir`, `test-changed`; project folder meant to be committed; home `~/.kairos-cfg/config` takes `model.` lines only). Read order per setting: `.kairos-cfg/config` in the project, then the older per-setting files (`.kairos-cfg/models` etc.), then `.kairos/.models`/`.manual-qa`/`.qa-dir`, then, for `model.` only, the home folder, then the agent's `model:`. `model.` lines merge per agent; aliases only (`opus`, `sonnet`, `haiku`, `fable`); read at each dispatch and passed as the Agent call's `model` parameter (and at both Step 0e dispatches); reaches only agents the orchestrator dispatches (including the lead and layer agents). The orchestrator writes only inside `.kairos/`; only `/kairos:setup` writes `.kairos-cfg/` (and only `model.` lines). No secret ever goes in `.kairos-cfg/`; the orchestrator reads only the three named settings. `manual-qa` and `qa-dir` are asked lazily at the gate that needs them (trim and lowercase when reading). `test-changed` is read by the agents, not the orchestrator (project `config` only; command with `{files}` or `off`). `docs/customizing.md` is the one page listing every setting.
- **Test economy** (`skills/test-scope/SKILL.md`): scope ladder test files → related tests → full suite; the full run has one owner per stage (TDD implementer's last planned wave, the verifier's first run when it has no run to reuse, the loop's final pass, the lead's first close); everything else goes narrower; a targeted run carries the last full run's `coverage_summary` and writes `execution.scope: targeted`. Tests are written one per behaviour an `AC-n` or risk names.

## Artifacts and the ledger

Every phase writes one Markdown file: YAML frontmatter with only what the orchestrator branches on (verdict, tallies its status rules threshold, loop signal), then a Markdown body opening with a `## Summary` block (`skills/artifact-template`). No phase output is JSON. Risks/Issues/Findings tables carry a `Disposition` column. Derived `status` and per-Impact tallies follow `skills/artifact-bookkeeping`; its §4 required-frontmatter table is also read by the orchestrator's Artifact Contract Check. Underscore-prefixed files carry no `status` or Disposition table.

Artifacts land in `.kairos/<feature_folder>/` of the target project. Each folder has `ledger/` with `constraints.md`, `decisions.md`, `open-questions.md` (agents read at phase start, update at phase end; each phase updates only its own rows; the full re-walk runs twice, at `architect-agent` and `release-planner-agent`), plus orchestrator-only `run.md` and `loops.md`. Folders written before v8.4.0/v8.5.0 must keep resuming: every reader falls back to the older location or format and the orchestrator migrates on first touch. Only the orchestrator writes `decisions.md`'s `Supersedes` column. `constraints.md` has a `Category` column from `skills/constraint-taxonomy` written once at row creation; three checks gate on it (Accessibility, Compliance & Privacy, Cross-Environment Verification). Undeclared means `N/A`; an obligation is never inferred from code. A `VERIFICATION` row names its `AC-n`, which lets `test-verifier-agent` classify it as verified elsewhere. `pm-agent` writes `## Slices` (step 4c) when the work lands in several steps; every criterion belongs to exactly one slice; `test-verifier-agent`'s fourth state `later — <slice>` is never a gap.

Project-root exceptions (persist across features; one writer each): `.kairos/_lessons.md` (`retrospective-agent`), `.kairos/decisions/` (`improvement-advisor-agent`), `.kairos/_tech-debt.md` (`dependency-audit-agent`), `.kairos/_qa-regression.md` (`qa-plan-agent`).

## Layered Mode (`agents/team/`)

Replaces Phase 3's single implementer with a lead (`implementer-lead-agent`) and up to four layer agents (`teammate-tests-agent`, `-backend-`, `-frontend-`, `-database-`). Claude Code only, no Agent Teams, no flag. Offered only when the TDD path was chosen, two or more of backend/frontend/db are touched and the host is Claude Code (the cost question stays). The orchestrator is the coordinator; all stages are plain subagent calls. Details: `skills/orchestrator-layered/SKILL.md`.

Stages: 3a lead writes `03-contracts.md` and the plan, spawns nothing; **RED** (`teammate-tests-agent`, alone) → **GREEN** (one call per in-scope layer in one message) → **VERIFY** (lead; compliance against contracts) → **FIX** (only layers the verify named, then verify again) → **REFACTOR** → **CLOSE** (lead; re-verify, ledger update, `03-implementation.md` last). A review-loop or post-gate fix pass runs `scope` (lead) → `fix` (layers) → `close`.

Rules: one runner of the suite (GREEN layers run static checks on their own files at most; the full run has one owner per `skills/test-scope`; RED runs alone and may run its own new tests; VERIFY probes the test environment first and reports an `Environment:` row). One writer of shared state: only the lead writes the ledger and `03-contracts.md`; only the orchestrator writes `run.md`; each layer writes `03-layer-<layer>.md`; handoff on disk, dispatch prompts carry only `key: value` lines (`Feature folder:`, `effort:`, `step:`, `layer:`, `round:`). A subagent has no `AskUserQuestion`: contract mismatches are rows of the plan's `## Risks` table resolved by the orchestrator's loop; a `Mitigate now` row is applied by the lead to `03-contracts.md`. The orchestrator keeps `layered_stage` and `layered_round` (cap 2 repeats per contract field); a missing `layered_stage` means no run started. Layer agents create files with Write/Edit (never `cat >` or a heredoc), give any command that may run past two minutes an explicit `timeout`, and treat a command the host moved to the background as hung, naming it in `## Notes`. `03-layer-*.md` and `03-verify.md` are supporting artifacts, ignored for the resume point, archived with a run, removed by the cleanup gate. A wait line carries stage, round, wave, agents, start time and last same-stage time.

## Deliberately Out of Scope

KAIROS covers planning through verification. It does **not** cover deployment execution, post-deploy verification, observability-as-code, production incident response, load testing, or cost analysis. `release-planner-agent` produces a deployment *plan* and stops. Those activities need credentials a distributed framework cannot assume, deployed environments and continuous presence, and the feasible parts would each add a writer outside `.kairos/`. Static performance review stays in scope in `code-reviewer-agent`'s Performance check. Revisit this boundary before adding an agent that executes a deploy, applies an infrastructure change or polls a live environment.

## VitePress Site (`docs/`)

Config in `docs/.vitepress/config.js` (reads `version` from `package.json`, injects it site-wide; sidebar and nav defined there). `srcDir` is `..` (repo root), so Markdown comes from the whole repo; `CHANGELOG.md` is rewritten to `changelog.md` via `rewrites`. `docs/agent-files.md` and `docs/agent-files-team.md` embed raw agent Markdown and must stay in sync. `internal/` is gitignored and not published.

## Skills (`skills/`) and Commands (`commands/`)

Skills ship in the plugin. Shared references: `contract-checklist`, `threat-model`, `migration-safety`, `constraint-taxonomy`, `analysis-discipline`, `coding-discipline`, `code-simplification`, `test-scope`, `issue-text`, `artifact-bookkeeping`, `artifact-template`, `issue-tracker-comment`, `agent-contract`. Five `orchestrator-*` skills (`-resume`, `-run-choices`, `-writeback`, `-layered`, `-closeout`) hold branch-only text moved unchanged out of `agents/orchestrator-agent.md`, each left there as a one-paragraph stub saying when to read it; read by the orchestrator alone, not mirrored (a mirror body carries the stub and the same relative link).

Commands (Claude Code only, not mirrored): `/kairos:setup` (per-tier model setup into `.kairos-cfg/config`), `/kairos:view` (renders one phase artifact as HTML via the Artifact tool, one file per call), `/kairos:usage` (model and token buckets per dispatched agent, measured from the host's subagent transcripts by `scripts/usage.mjs`; best effort since the transcript format is undocumented; response counted once, four token buckets kept apart).

Token-cost levers are documented in `docs/customizing.md` ("Keeping token use down"); the user's constraint is token volume, not price.

## Plugin (`.claude-plugin/`)

`plugin.json` carries its own `version`. **Bump `package.json` and `plugin.json` together** when releasing.

## Deployment

Netlify, only from a version tag: `.github/workflows/deploy-docs.yml` POSTs the `NETLIFY_DEPLOY_HOOK` secret on any `v*` tag push; `netlify.toml` holds the real build (`npm run docs:build` → `docs/.vitepress/dist`, Node 22). Pushing to `main` or `develop` deploys nothing.

## Compatibility

kairos-cli (the runner, separate repo with its own version line, independent of KAIROS's) implements the deterministic rules in code and pins a tagged KAIROS commit; its docs need aligning after each tag. Nothing there is edited from here.
